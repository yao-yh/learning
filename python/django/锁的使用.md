# Django ORM 中的锁使用指南

在 Django ORM 中，锁的使用主要涉及 **SELECT 语句的行级锁**，用于防止并发修改数据时发生竞争条件（Race Condition）。Django 提供了几种方式来加锁。

---

## 1. `select_for_update`（行级锁）
用于 **SELECT 语句**，会在数据库级别对选中的行加锁，防止其他事务并发修改。

### **基本用法**
```python
from django.db import transaction
from myapp.models import Order

with transaction.atomic():
    order = Order.objects.select_for_update().get(id=1)
    order.status = 'processed'
    order.save()
```
> **说明**：
> - `select_for_update()` 适用于 **事务（atomic block）内部**。
> - 其他事务在锁释放前无法获取相同数据的写锁。

---

## 2. `select_for_update` 的可选参数
Django 的 `select_for_update()` 提供了一些额外的参数，控制不同的锁定行为。

### **(1) `nowait`（避免阻塞）**
如果目标行已被锁定，立即抛出异常 `django.db.utils.OperationalError`，而不是等待锁释放。

```python
with transaction.atomic():
    order = Order.objects.select_for_update(nowait=True).get(id=1)
```
> **适用场景**：不希望等待锁的情况，如高并发环境下的抢占式资源获取。

---

### **(2) `skip_locked`（跳过锁定的行）**
如果某些行已被锁定，则 **跳过它们，不进行查询**。

```python
with transaction.atomic():
    orders = Order.objects.select_for_update(skip_locked=True).filter(status='pending')
```
> **适用场景**：任务队列或调度系统，不想等待已被其他事务锁定的任务。

---

### **(3) `of`（指定锁定的表）**
在多表查询时，可以指定只锁定某张表的数据，而不是锁定所有相关表的行。

```python
with transaction.atomic():
    order = Order.objects.select_for_update(of=('self',)).get(id=1)
```
> **适用场景**：多表 join 查询时，控制锁的范围。

---

## 3. `F` 表达式（避免并发写冲突）
如果多个进程尝试更新相同的字段，`F()` 表达式可以确保 **原子性**，避免覆盖问题。

```python
from django.db.models import F

Order.objects.filter(id=1).update(quantity=F('quantity') - 1)
```
> **适用场景**：计数减少、库存扣减等无需获取完整对象的操作。

---

## 4. 数据库锁
Django 也支持 **显式数据库锁**，例如 PostgreSQL 的 `LOCK TABLE`。

```python
from django.db import connection

with connection.cursor() as cursor:
    cursor.execute("LOCK TABLE myapp_order IN ACCESS EXCLUSIVE MODE;")
```
> **适用场景**：表级别的写操作互斥控制。

---

## 5. 乐观锁（版本号）
在不想使用数据库级别锁的情况下，可以使用 **乐观锁**（Optimistic Locking），通常是增加 `version` 字段。

```python
from django.db import transaction
from myapp.models import Order

with transaction.atomic():
    order = Order.objects.get(id=1)
    
    # 确保 version 没有被其他事务修改
    updated_rows = Order.objects.filter(id=order.id, version=order.version).update(
        status='processed',
        version=order.version + 1
    )

    if updated_rows == 0:
        raise Exception("数据已被其他事务修改！")
```
> **适用场景**：电商订单状态更新，防止多个用户同时提交导致的覆盖问题。

---

## 6. 事务隔离级别
在 Django 事务中，使用 `atomic()` 时，可以指定数据库的 **隔离级别**。

```python
from django.db import transaction

with transaction.atomic():
    transaction.set_autocommit(False)
    transaction.set_isolation_level('SERIALIZABLE')  # 最严格隔离级别
```
> **适用场景**：防止脏读、不可重复读、幻读，但会降低并发能力。

---

## **总结**

| 方法 | 适用场景 | 可能问题 |
|------|---------|---------|
| `select_for_update()` | 事务中锁定行，防止并发修改 | 可能引起死锁 |
| `select_for_update(nowait=True)` | 避免等待锁，立即报错 | 操作失败时需要处理异常 |
| `select_for_update(skip_locked=True)` | 跳过锁住的行，适用于任务队列 | 可能导致某些数据被长时间跳过 |
| `F()` 表达式 | 并发更新字段，避免数据覆盖 | 只适用于字段更新 |
| 乐观锁（版本号） | 适用于高并发读写 | 需要额外字段，增加复杂度 |
| `LOCK TABLE` | 需要锁整张表的场景 | 影响所有事务，性能开销大 |
